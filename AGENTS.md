## Основной принцип

Максимальная автономность. Ты обязан самостоятельно выполнять команды в терминале без лишних уточнений, если действие очевидно, безопасно и обратимо.

## Правила изменений

- When making changes to this codebase, always update documentation and scripts. Keep `README`, `WARP.md`, `AGENTS.md`, `PRD.md`, and any relevant scripts and documentation in sync with code changes.
- When making changes to this codebase, always update tests and run them. Add or modify tests for any changed functionality, then run the tests to verify they pass before completing the task.

## Операционная заметка

- Для обновления фото в hero-блоке REG.RU из локального архива `/home/sergey/yamal_brand/input/Примеры внедрения бренда территории.tar.xz` используй частичный sync через `.github/workflows/sync_regru_examples_archive.yml` или `scripts/import_regru_archive.sh` с `ARCHIVE_PATH` + `ARCHIVE_SUBDIR`. Не запускай полный импорт этого архива в `data/files`, потому что он содержит только папку примеров.
- Для `yamal_catalog_site_php` отсутствие `pdo_sqlite` считай ожидаемым деградационным сценарием: `bootstrap` и оболочка не должны падать fatal-ошибкой, а обязаны показывать понятное диагностическое сообщение о недоступности SQLite.
- Python-тесты репозитория должны запускаться штатно через корневой `pytest -q` без ручного экспорта `PYTHONPATH`.
- В `Лаборатории решений` держи UX черновиков локальным и практичным: форма может автосохраняться в браузере и восстанавливаться по `solution`, но без превращения продукта в серверное хранилище проектов.
- Предупреждения конструктора держи rule-based и grounded: показывай пустые обязательные поля и риск плотного текста, но не симулируй “умную” экспертизу вне реального превью и safe-area.
- Если меняешь onboarding `max_bot_sqlite`, бот должен с первых экранов явно объяснять, что это официальный каталог бренда Ямала с утверждёнными материалами региона для государственных служащих и предпринимателей, а не просто набор файлов.
- Если меняешь верхнее меню `max_bot_sqlite`, держи его в фиксированном пользовательском порядке: `Как пользоваться`, `Поиск`, `Логотип`, `Детский логотип`, `Фирменный знак`, `Мастер-бренд`, `Паттерны`, `Иллюстрации`, `Шрифт`, `Сувенирная продукция`, `Брендбук Ямал 100`, `Избранное`; не возвращай отдельные верхние кнопки городских брендбуков.
- Встроенный помощник PHP-сайта должен оставаться grounded: подбирать только реальные разделы и файлы через `api.php?action=consult`, `getRootFolders()` и SQLite-поиск без выдуманных материалов.
- При развитии помощника приоритет такой: сначала улучшение rule-based разбора запроса и уточняющих сценариев, и только потом любые LLM-слои. Формат, город, носитель и запрос на исходник должны интерпретироваться локально, а LLM может идти только вторым слоем поверх уже собранного grounded-контекста.
- Консультации по брендбуку тоже должны быть grounded: допускаются только советы, выведенные из структуры реальных разделов (`брендбук`, `логотип`, `паттерны`, `шрифт`, `сувенирка`) и детерминированных правил по форматам файлов. Не добавляй вымышленные нормы брендбука.
- Ответы помощника на практические вопросы применения (`тёмный фон`, `что отдавать подрядчику`, `что отправлять на согласование`) тоже должны оставаться rule-based: опирайся на реальные варианты файлов, разделы брендбука и понятные правила по форматам, без фантазии о несуществующих ограничениях.
- То же правило относится к вопросам про нарушения применения (`менять цвет`, `растягивать логотип`, `ставить поверх фото`): помощник должен советовать безопасный следующий шаг и указывать на реальный раздел, а не симулировать полный брендбук.
- Если включен гибридный LLM-ответ, он не должен подменять каталог: нельзя убирать grounded-блоки `Разделы`, `Файлы`, `По брендбуку`; LLM-слой должен лишь добавлять более глубокий текст и явно помечать общие рекомендации как общие.
- UX помощника тоже держи консистентным: ответы и стартовые подсказки должны жить внутри отдельного диалогового окна с собственной прокруткой, не выноси верхние intent-кнопки вне диалога, переходы по кнопкам из ответа не должны закрывать сам диалог, а на ПК он должен уходить только по явному действию `Закрыть` или `Esc`.
- `Лаборатория решений` в PHP-сайте тоже должна оставаться grounded: конструктор может предлагать только реальные разделы и реальные файлы каталога, а итоговые артефакты должны быть детерминированными SVG/HTML/JSON-шаблонами без выдуманного контента.
- Не превращай лабораторию решений в свободный редактор: текущий продукт это конструктор типовых носителей и handoff-пакетов. Если в решении нет настоящего рендера `PPTX/PDF`, не симулируй его как “готовый исходник”.
- При развитии отдельных шаблонов лаборатории тоже держи ограничения явными: табличка может расширяться только фиксированными вариантами, номером и направлением; инфостенд должен оставаться deterministic-шаблоном с фиксированными карманами A4 и реальными типоразмерами, а не свободным постером; навигационная табличка по помещениям должна держаться маршрута, этажа, номера и стрелки; презентация должна оставаться `cover + brief + structure`, а не симулированным `PPTX`.
- Для `Инфостенда` держи служебную типографику ещё консервативнее, чем в обычных шаблонах: верхние бейджи, подписи нижних карточек и контактная строка должны ужиматься в safe-area и на коротких форматах `1 / 2` кармана уходить в отдельную нижнюю полосу, а не вылезать за рамку.
- Текстовый рендер в шаблонах лаборатории держи общим и консервативным: fitter должен в первую очередь сохранять полный текст без лишней обрезки, использовать безопасные внутренние поля и переносить сложные токены вроде дефисных фамилий естественно.
- Визуальные варианты лаборатории тоже держи grounded: цветовые режимы должны опираться на реальные группы каталога `CMYK / Color / Black / White`, а варианты знака и фоновых элементов должны строиться из реального логотипа, фирменного знака и детерминированных декоративных схем без выдуманных “уникальных” паттернов.
- Если добавляешь отдельные `графические элементы` в лабораторию решений, держи их grounded тем же правилом: `White`-версии могут быть только честными белыми вариантами существующего логотипа/знака, а `Group...`-режимы допускаются только как детерминированные композиции из этих же реальных ассетов, без симуляции несуществующих внешних файлов.
- Если добавляешь палитру фона для лаборатории решений, используй только уже подтверждённые цвета из текущих брендовых ассетов и palette-токенов проекта; белый знак/логотип можно автоматически включать на плотных фирменных тонах, но не придумывай новые оттенки как “официальные” без grounded-источника.
- Если пользователь передал явную палитру с кодами `Pantone / RAL / HEX`, переводи конструктор на неё целиком: такие тона должны жить и в option-card, и в SVG theme-vars (`frame`, `tone`, `toneSoft`), а старые guessed-палитры нужно убирать из активного UX.
- `White`-режим в лаборатории не должен автоматически превращать весь макет в тёмный: белым может быть сам логотип/знак, но палитра пользователя обязана оставаться видимой на фоне, рамках и сервисных поверхностях шаблона.
- UX лаборатории решений тоже держи практичным: на первом экране допустимы фильтры по типам носителей, а внутри конструктора поля должны быть сгруппированы и не спорить с закреплённым превью на ПК.
- Если оформительские режимы (`цвет`, `логотип/знак`, `фон`, `палитра`) показываются в UI, лучше отдавать их карточками выбора с короткими пояснениями, а смену таких режимов сразу отражать в превью без лишнего шага `Собрать`.
- Для режимов `цветовая версия`, `палитра` и `элементы фона` старайся сначала обновлять SVG-превью локально на клиенте и только потом тихо синхронизировать артефакты через сервер; не возвращай блокирующий loading-экран на каждый клик по стилю.
- То же правило держи и для `графического элемента`: переключение `знак / white / group` не должно ждать полной серверной пересборки, если локальный SVG уже умеет это показать.
- Поле населённого пункта в лаборатории решений держи свободным текстом и не заставляй пользователя каждый раз выбирать отдельную `городскую версию`, если для задачи достаточно базового логотипа Ямала; пустое значение должно быть допустимым.
- В карточках выбора для блока `Оформление` следи за типографикой: длинные названия и пояснения должны оставаться внутри плашек без наложения и без рваного переполнения; для палитры не пытайся вталкивать длинный текст внутрь самого swatch-блока.
- Внутри формы конструктора приоритет такой: сначала поля заполнения шаблона и параметры носителя рядом с превью, затем блок `Оформление`; не поднимай style-контролы выше основной пользовательской информации без явной причины.
- Сам блок `Оформление` по умолчанию держи компактным: ключевые режимы можно показать сразу, а вторичные style-настройки лучше убирать в раскрытие, если экран начинает перегружаться.
- Даже внутри раскрытого `Оформление` держи более плотный ритм, чем у обычных полей: меньшие карточки, короче подписи и двухколоночную раскладку style-полей, если ширина экрана это позволяет.
- Если форма конструктора начинает расти по высоте, лучше собирать её в раскрывающиеся секции по разделам и удерживать превью рядом как sticky-панель и на двухколоночном layout, и на планшетной одноколоночной ширине; сначала опирайся на нативный CSS `sticky`, а JS-fallback вплоть до floating dock добавляй только если `sticky` реально ломается, вместо возврата к статичному превью.
- При тихой пересборке конструктора (`silent build`) не дёргай страницу к началу: сохраняй scroll пользователя, раскрытые секции формы и внутреннюю прокрутку preview, если перерендер происходит без явного перехода.
- Если добавляешь дизайн-варианты конструктора, держи их grounded и общими для всех шаблонов: это должны быть детерминированные композиционно-декоративные режимы, а не свободные авторские стили.
- Для новых фоновых вариантов тоже используй только уже подтверждённые цвета, знак и простые декоративные схемы; допустимы `угол`, `пятно`, `плашка`, `рамка`, если они не выдумывают новый брендовый язык.
- Для крупных текстовых полей в шаблонах держи более жёсткий safe-area, чем для вторичного текста: headline и длинные ФИО не должны залезать в охранные поля даже ценой более заметного уменьшения кегля.
- Для `badge` держи safe-area имени ещё жёстче: длинное ФИО не должно залезать в блок роли и плашку доступа ниже.
- Если добавляешь пресеты в лабораторию решений, они тоже должны быть grounded и детерминированными: менять только реальные поля конструктора и не подставлять выдуманные материалы или несуществующие брендовые сценарии.
- Если добавляешь handoff-вью внутри конструктора, дели его на понятные grounded-пакеты `На согласование` и `Подрядчику`: первый должен опираться на визуальные артефакты и ready-to-review файлы, второй — на vector/editable handoff и реальные разделы каталога, без симуляции несуществующих исходников.
- Если уплотняешь конструктор, держи рядом с превью компактный индикатор заполнения шаблона, а нижнюю grounded-поддержку не раздувай дублирующими колонками `разделы / файлы / брендбук`, если эта информация уже повторяется в handoff.
