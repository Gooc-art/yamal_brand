# PRD

## Продукт

Веб-сервис бренд-материалов Ямала на PHP + SQLite для shared hosting.

Смежный продукт в том же репозитории:
- `max_bot_sqlite` должен вести пользователя как в официальный каталог бренда Ямала и с первых экранов объяснять, что это утверждённые материалы бренда региона для государственных служащих и предпринимателей
- верхнее меню `max_bot_sqlite` должно быть коротким и стабильным: без отдельных верхних кнопок для городских брендбуков и с фиксированным порядком основных сценариев входа

## Основные сценарии

1. Найти раздел или файл каталога.
2. Открыть карточку материала, просмотреть и скачать файл.
3. Получить grounded-консультацию по брендбуку и следующему шагу.
4. Собрать типовой носитель через `Лабораторию решений`.
5. Если на хостинге временно отсутствует `pdo_sqlite`, сайт должен показать явную диагностическую причину и не падать fatal-ошибкой на `bootstrap`.

## Лаборатория решений

Цель:
- ускорить выпуск типовых бренд-носителей без запуска отдельного графического продукта

MVP:
- формы для заполнения данных по носителю
- группировка полей и простой пошаговый UX внутри конструктора
- фильтры по категориям носителей на первом экране лаборатории
- генерация стартового SVG/brief-пакета
- углубленные handoff-сценарии для отдельных носителей:
  табличка с типом, номером и стрелкой; инфостенд с фиксированными карманами A4 и размерами `1 / 2 / 4 / 6 / 8 / 10 / 12` карманов; навигационная табличка по помещениям с этажом и маршрутом; презентация со сценарием, тезисом и структурой слайдов
- у `Инфостенда` служебные подписи должны быть особенно консервативными на коротких форматах: верхние бейджи, заголовки нижних карточек и нижняя контактная строка не должны выходить за рамку даже ценой более плотного кегля и отдельной нижней полосы
- единый слой оформления по всем шаблонам:
  цветовые варианты `CMYK / Color / Black / White`, выбор `логотип с надписью / фирменный знак`, управляемые фоновые элементы и явные подписи сервисных блоков
- grounded-палитра фона внутри конструктора:
  только подтверждённые тона из переданной палитры: `Фирменный красный / Pantone 193 C`, `Мамонтовая кость / Pantone 7506 C`, `Ягель снежный / Pantone 5245 C`, `Pantone 621 C`, `RAL 6034`; они должны работать как фоны и рамки, а на плотном красном логотип/знак может автоматически уходить в белую версию
- у style-слоя должен быть отдельный grounded-переключатель `Графический элемент`: `Знак Ямал`, `Фирменный знак White`, `Фирменный знак + Ямал White` и детерминированные group-композиции `Group 1410103616 / Group 2087328779 / Group-1`, собранные только из реального логотипа и фирменного знака
- композиция шаблона может перестраиваться от выбранных элементов:
  знак должен давать другой визуальный каркас, чем логотип с надписью
- style-режимы в форме должны показываться не обычными select, а визуальными карточками выбора; смена таких режимов должна сразу обновлять превью
- для `цветовой версии`, `палитры` и `элементов фона` это обновление должно быть визуально мгновенным: локальный preview меняется сразу, а серверная сборка синхронизирует артефакты без блокирующего loading-экрана
- то же правило относится к `графическому элементу`: переключение между знаком, white-версией и group-композицией должно быть видно в SVG-превью сразу, без отдельной полной загрузки
- обычные кнопочные сценарии каталога тоже должны быть диагностируемыми: если `раздел`, `поиск` или `карточка файла` не получили данные, пользователь должен видеть понятный retry-state с причиной и кнопкой повтора, а не “мертвую” кнопку
- инфраструктурные проблемы PHP-окружения тоже должны проявляться явно: отсутствие `pdo_sqlite` не должно ронять API на `500` без пояснения, пользователь должен видеть диагностический banner о недоступности SQLite-каталога
- поле населённого пункта в конструкторе должно быть свободным текстом без жёсткого select по городским версиям; если населённый пункт не указан, базовый макет не должен насильно показывать `Ямал` как отдельную выбранную версию
- порядок формы должен быть прагматичным: сначала заполнение шаблона и параметры носителя рядом с превью, затем блок `Оформление`
- `White`-вариант не должен насильно переводить весь макет в тёмную тему: белый логотип/знак может быть reversed-asset, но выбранная палитра обязана оставаться видимой на фоне и сервисных поверхностях шаблона
- блок `Оформление` должен быть двухуровневым: `логотип / графический элемент / дизайн / фон / палитра` видны сразу, а вторичным раскрытием остается только `цветовая версия`
- даже в раскрытом состоянии `Оформление` не должно раздуваться: style-карточки и подписи должны быть плотнее обычных полей, а сами style-поля могут идти в две колонки на достаточной ширине
- состояние нажатия должно быть читаемым: кнопки, карточки пресетов и выбор стиля должны давать явный pressed-state на мыши и touch, а не выглядеть одинаково до и после тапа
- визуальная система конструктора должна быть материальной и спокойной: вместо стеклянных полупрозрачных плиток нужны бумажные поверхности, чёткие рамки и ограниченные фирменные акценты
- крупные секции формы тоже должны сворачиваться по разделам, а preview должен оставаться рядом со скроллом формы как sticky-панель и на двухколоночном layout, и на планшетной одноколоночной ширине, пока пользователь листает длинные настройки; основной режим должен опираться на нативный CSS `sticky`, а JS-fallback вплоть до компактного floating dock нужен только для браузеров, где `sticky` реально не держится
- на мобильной ширине превью тоже по возможности должно оставаться sticky и прокручиваться внутри собственной панели, вместо полного возврата к статичному блоку над формой
- тихая server-sync пересборка конструктора не должна сбрасывать scroll пользователя: при `silent build` нужно сохранять положение страницы и состояние раскрытых секций формы
- у конструктора должны быть grounded дизайн-варианты `спокойный / редакционный / акцентный / плакатный`, которые меняют декоративный слой и визуальный ритм без превращения продукта в свободный редактор
- фоновые варианты тоже могут расширяться детерминированными схемами вроде `углового акцента` и `мягкого пятна`, если они строятся из уже существующих брендовых цветов и знака
- поверх этого допустим более сильный общий style-layer: `монументальный / маршрутный / галерейный`, а также дополнительные фоновые схемы `разделённая сцена / опорная рейка / капсулы`, если они одинаково применимы ко всем шаблонам и собраны из реальных брендовых элементов
- набор `графических элементов` можно расширять только детерминированными композициями из существующего логотипа и знака: например ритмическая лента логотипов, каскад знаков и тандем логотипа со знаком
- палитра должна влиять на реальные theme-vars SVG, а не только на swatch в интерфейсе: выбранный тон обязан доходить до рамок, мягких подложек, линий и lockup-панелей
- типографика этих карточек выбора должна оставаться аккуратной: длинные названия и пояснения не должны вылезать или накладываться внутри плашек, а палитра не должна тащить длинный текст внутрь цветового swatch
- у каждого носителя должны быть короткие grounded-пресеты сценариев, которые одной кнопкой переключают типовой режим `официальный / печать / контраст / навигация / питч`
- после сборки результат должен делиться на два grounded handoff-пакета:
  `на согласование` и `подрядчику`, чтобы preview/brief и production-исходники не смешивались
- рядом с превью должен быть явный индикатор заполнения шаблона: сколько полей уже заполнено и хватает ли обязательных значений
- форма конструктора должна сохраняться локально в браузере и автоматически восстанавливаться при повторном открытии того же решения без серверного хранения проектов
- рядом с превью нужны явные rule-based предупреждения: какие обязательные поля пусты, где текст уже близок к границам safe-area и почему перед handoff стоит открыть SVG вручную
- пользовательский текст внутри лаборатории должен быть прямым и прикладным: вместо сервисных слов вроде `handoff` показываются названия действий уровня `Что скачать и открыть`, `Подходящие разделы`, `В работу`
- рядом с `SVG` в конструкторе должна быть быстрая выгрузка в `PNG`, но только как raster-export из текущего SVG-превью без отдельной симуляции нового исходного формата
- адаптивная типографика SVG-превью, чтобы текст оставался в пределах полей и не ломал макет на длинных значениях
- сами превью-шаблоны не должны засоряться сервисным текстом: метаданные носителя, тип крепления, размер, внутренние названия секций и helper-лейблы карманов должны оставаться в UI/brief, но не печататься внутри итогового макета
- для `сертификата` официальный сценарий должен опираться на чистый документный каркас: центральную надпись `Ямал`, лёгкую рамку и более строгую типографическую иерархию вместо тяжёлой верхней плашки
- у `Бейджа` зона имени должна быть особенно консервативной: длинные ФИО не должны залезать в блок роли и нижние сервисные элементы
- единый fitter по всем шаблонам, который предпочитает полный текст без ложной обрезки, использует защитные внутренние поля и естественные переносы для сложных строк
- крупные headline-поля в digital и event-шаблонах должны использовать ещё более консервативный safe-area режим, чтобы длинные заголовки и ФИО не заходили на охранные поля
- адаптивный preview-shell по пропорциям носителя и нормализованные сетки действий внутри конструктора
- упрощённый верхний вход в лабораторию: карточки без вторичных форматных меток и без перегруженных filter-chips
- короткие operational-summary на карточках решений вместо длинных описаний на первом экране
- рекомендации по реальным разделам и реальным файлам каталога
- draft-состояние конструктора не должно разрастаться в три длинные колонки: для старта достаточно одного компактного grounded-блока, а полные файлы и разделы после сборки должны жить уже в handoff
- deep link на конкретное решение

Не входит в текущий MVP:
- полноценный WYSIWYG-редактор
- фоновая очередь сложного рендера
- генерация `PPTX` и сложного production-ready `PDF`
