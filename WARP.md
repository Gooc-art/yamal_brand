## Web Service Focus

Активный продукт в этом репозитории: `yamal_catalog_site_php`.

Операционные границы проекта:
- работать только с официальным MAX-ботом проекта `https://max.ru/yamalbrend_bot`
- использовать только репозиторий `https://github.com/Gooc-art/yamal_brand`
- не переходить в другие проекты, репозитории, боты или сервисные контуры без явной отдельной команды пользователя

Текущий контур:
- PHP + SQLite каталог бренд-материалов
- многостраничный бренд-портал с route pages `/`, `/catalog`, `/branding-catalog`, `/editor/<id>`, `/constructor/layouts`, `/constructor/requests`, `/admin`; каталог брендирования и редактор доступны гостям
- `/catalog` открывает видимую рабочую область каталога сразу, а query-маршруты внутри каталога восстанавливают папку, поиск или карточку файла
- главное меню по реальным разделам каталога
- поиск, deep links, карточка файла, предпросмотр и скачивание
- grounded-помощник по каталогу и брендбуку
- `Лаборатория решений` для типовых носителей
- локальный browser-only кабинет с регистрацией, входом, редактированием профиля и связью с локальными черновиками конструктора
- серверный админ-вход сайта включается только через `ADMIN_EMAIL` и `ADMIN_PASSWORD_HASH` / `ADMIN_PASSWORD` в `.env`
- защищённые страницы сайта должны проверять локальную авторизацию на клиенте, а `/admin` дополнительно роль `Admin`; прямые URL обслуживаются через `.htaccess` / `router.php`
- для `Бейджа с фото` фото профиля из кабинета подставляется автоматически, но пользователь может заменить его в редакторе только для текущего макета
- пользовательский логотип в конструкторе загружается только через обычный file input с проверкой типа и мгновенным предпросмотром
- при отсутствии `pdo_sqlite` PHP-сайт не должен падать fatal-ошибкой: оболочка и `bootstrap` обязаны открываться с явным диагностическим сообщением, а каталоговые данные могут временно деградировать в пустой ответ
- корневой `pytest -q` по репозиторию должен запускаться без ручного `PYTHONPATH`
- у конструктора лаборатории должен быть локальный autosave черновика по `solution`, автоматическое восстановление формы и явные rule-based предупреждения рядом с превью

Смежный контур:
- `max_bot_sqlite` должен объяснять себя как официальный каталог бренда Ямала, а не как абстрактный набор файлов; стартовый onboarding для бота должен явно проговаривать, что это каталог утверждённых материалов для госслужащих и предпринимателей
- главное меню `max_bot_sqlite` должно оставаться коротким и предсказуемым: `Как пользоваться`, `Поиск`, ключевые бренд-разделы, `Шрифт`, `Сувенирная продукция`, `Брендбук Ямал 100`, `Избранное`, без отдельных верхних кнопок городских брендбуков
- у `max_bot_sqlite` должен быть закрытый админ-отчет: новые пользователи за последние 7 дней, общее число пользователей за все время, общее число взаимодействий, общее число скачиваний файлов (`send_file`) и самые частые поиски/открытия по runtime-данным
- для файлов `PNG`, `JPG/JPEG` и `PDF` первый клик должен открывать предпросмотр/карточку с кнопкой `Скачать`; статистика `send_file` должна расти только после фактической отправки исходного файла
- папки-варианты с набором форматов должны показывать реальный предпросмотр из доступного `PNG/JPG/PDF` файла этой же папки на первой странице, а ниже оставлять выбор формата
- на старте `max_bot_sqlite` должен публиковать MAX-команды и писать только обезличенные `[update]` metadata в journal, чтобы можно было диагностировать системный `Start`, `/start` и callback-кнопки без раскрытия текста сообщений и токена
- старт `max_bot_sqlite` должен заранее валидировать `CATALOG_DB_PATH`, `RUNTIME_DB_PATH` и `CATALOG_ROOT_PATH`, а диагностика должна показывать отсутствующую базу или папку без вывода токена
- перенос `max_bot_sqlite` на `BOTSGSN` выполняется workflow `Migrate Yamal MAX Bot To BOTSGSN` внутри `Gooc-art/yamal_brand`: сначала сухой deploy без старта сервиса, затем старт на новом runner `yamal-botsgsn`, и только после ручной проверки остановка старого `yamal-max-prod`
- аварийное восстановление GitHub runner BOTSGSN запускается на отдельном repository runner с label `yamal-control`; workflow обязан сначала быстро проверить доступность `10.10.68.10:22`, чтобы не зависать на недоступном SSH

## Лаборатория решений

Сейчас поддерживаются:
- визитка
- табличка
- инфостенд
- навигационная табличка
- презентация
- сертификат
- бейдж
- фирменный бланк
- пост для соцсетей
- роллап / стенд

Формат работы:
- пользователь заполняет поля
- поля сгруппированы по смыслу, а у лаборатории есть фильтры по типу носителя
- первый заход в конструктор использует облегчённый draft без тяжёлого file-search; полный подбор файлов включается уже на сборке
- открытие и сборка конструктора сами раскрывают workspace и в случае ошибки показывают retry-state, а не молчаливую пустоту
- при переключении между решениями старый конструктор должен убираться сразу; поздний ответ предыдущего `open/construct` не должен возвращать прошлый шаблон поверх нового
- тот же принцип нужен и для обычных пользовательских кнопок каталога: `раздел`, `поиск`, `файл` не должны тихо ломаться при сетевом или API-сбое, рабочая область должна уметь показать явный retry-state
- сайт собирает SVG/HTML/JSON handoff-пакет
- `Табличка` собирается как фиксированный кабинетный/навигационный/зональный шаблон
- `Инфостенд` собирается как фиксированный шаблон с карманами A4: `1 / 2 / 4 / 6 / 8 / 10 / 12` карманов и привязанными размерами стенда
- у `Инфостенда` служебные подписи тоже должны жить в более жёстком safe-area: верхние бейджи, названия нижних карточек и нижняя контактная строка обязаны ужиматься внутри рамки, а на коротких стендах `1 / 2` кармана получать отдельную нижнюю полосу
- `Навигационная табличка` собирается как отдельный маршрутный шаблон для коридоров и входных групп с этажом, номером и направлением
- `Презентация` отдает cover + brief со сценарием, тезисом и структурой слайдов
- для всех решений есть общий grounded-слой оформления: цветовые версии `CMYK / Color / Black / White`, переключение `логотип / фирменный знак` и набор фоновых режимов на базе реального знака и каталожной структуры брендбука
- у конструктора есть отдельная grounded-палитра фона из подтверждённых тонов: `accent / ivory / lichen / p621 / r6034`, то есть `Фирменный красный`, `Мамонтовая кость`, `Ягель снежный`, `Pantone 621 C`, `RAL 6034`; на плотном красном логотип и знак автоматически могут уходить в белую контрастную версию
- у style-слоя есть отдельный grounded-переключатель `Графический элемент`: `Знак Ямал`, `Фирменный знак White`, `Фирменный знак + Ямал White` и детерминированные композиции `Group 1410103616 / Group 2087328779 / Group-1`, собранные из реального логотипа и фирменного знака
- композиция шаблона тоже зависит от выбранных элементов: `фирменный знак` и `логотип с надписью` больше не обязаны делить одну и ту же раскладку
- в интерфейсе эти style-режимы собраны в карточки выбора с короткими пояснениями, а не в простые select; смена режима сразу пересобирает превью
- для `цветовой версии`, `палитры` и `элементов фона` превью должно меняться мгновенно на клиенте, а не через полный блокирующий перерендер всей сцены; сервер может тихо дособирать артефакты и handoff уже после локального обновления
- для `графического элемента` это поведение такое же: white-версии и group-композиции должны переключаться мгновенно внутри локального SVG-preview
- поле населённого пункта должно оставаться свободным текстом: без принудительного выбора городской версии и без обязательной отдельной подписи `Ямал`, если пользователь её не просил
- внутри формы конструктор должен вести сначала через заполнение шаблона и параметры носителя, а блок `Оформление` держать ниже как вторую фазу
- `White`-режим не должен ломать палитру: reversed-логотип может остаться белым, но сам макет обязан продолжать показывать выбранный тон фона, рамок и сервисных поверхностей вместо принудительной тёмной подложки
- сам блок `Оформление` лучше держать компактным, но заметным: `логотип / графический элемент / дизайн / фон / палитра` видны сразу, а во вторичный блок уезжает только `цветовая версия`
- внутри самого раскрытого style-блока тоже держи плотный ритм: меньшие карточки, более короткие подписи и две колонки для style-полей, пока экран это выдерживает
- интерактивность должна быть очевидной: кнопки, пресеты и choice-card'ы обязаны показывать заметный pressed-state, а выбранные варианты должны отмечаться сразу, без ожидания серверной пересборки
- UI лаборатории не должен уходить в glassmorphism: полупрозрачные квадраты и случайные мягкие блоки лучше заменять на бумажные поверхности, рамки, линии и спокойные фирменные акценты
- сами группы формы лучше держать раскрывающимися по разделам, а preview фиксировать рядом со скроллом не только в двухколоночном layout, но и в stacked-режиме; на широком экране достаточно нативного CSS `sticky`, а в одноколоночном конструкторе нужен отдельный floating dock, который включается сразу, как только блок шаблона дошёл до верхней кромки viewport
- на мобильной ширине превью тоже не должно проваливаться в полностью статичный блок: как только пользователь начинает уводить шаблон вверх, его лучше переводить в компактный dock, чем ждать полного исчезновения превью
- тихая пересборка конструктора не должна дёргать страницу: при `silent build` нужно сохранять scroll страницы, раскрытые секции и внутреннюю прокрутку preview-панели
- и явная сборка текущего решения тоже не должна выкидывать пользователя в общий loader сверху: если он уже внутри конструктора, экран надо держать на месте и обновлять in-place
- сам SVG-preview тоже не должен требовать отдельного внутреннего scroll: stage обязан поджимать макет целиком и показывать весь шаблон сразу
- в правой панели превью должно быть первым видимым блоком; прогресс, draft-status и предупреждения лучше держать уже под макетом
- при повторном открытии решения не прокручивай страницу к workspace, если он уже открыт: автопереход нужен только когда рабочая область ещё скрыта
- у конструктора теперь могут быть отдельные grounded дизайн-режимы (`calm / editorial / signal / poster`) и расширенные фоновые режимы (`corner / halo`), если они остаются детерминированными и строятся из текущих брендовых токенов и фирменного знака
- style-layer можно расширять и дальше, если режимы остаются grounded: допустимы новые общие варианты вроде `monument / navigator / gallery`, новые фоновые сцены `split / rail / capsule` и новые композиции из реального логотипа и знака вроде `logo_band / mark_constellation / lockup_bridge`
- типографика этих карточек выбора тоже держится консервативно: длинные названия и пояснения должны оставаться внутри плашек без наложения и рваного переноса, а палитра должна обходиться без тесного текста прямо внутри swatch
- в самих SVG держи охранную зону логотипа ещё строже: текстовые блоки не должны подплывать к верхнему lockup, а декоративные logo-композиции в `pattern/poster` лучше уводить к краям, а не в центр текста
- выбранная палитра должна менять не только UI-карточку, но и реальные frame/background theme-vars в SVG-превью, иначе пользователь видит ложный выбор цвета
- поверх полей есть быстрые grounded-пресеты по сценариям носителя: они одной кнопкой переключают рабочий режим без ручного клика по каждому параметру
- внутри конструктора handoff теперь делится на два сценария:
  `На согласование` и `Подрядчику`, чтобы visual/brief и production-исходники шли отдельными пакетами
- рядом с превью должен быть компактный индикатор заполнения шаблона, а не отдельный длинный summary-блок под формой
- нижняя поддержка конструктора должна оставаться компактной: в draft достаточно одного короткого grounded-блока с разделами и советом, а после сборки каталоговая часть должна жить уже внутри handoff
- в пользовательском UI избегай сервисных слов вроде `handoff`, если рядом есть более прямое название действия; для пользователя это должны быть блоки уровня `Что скачать и открыть`, `Подходящие разделы`, `В работу`
- кегль в SVG-полях подстраивается под доступный блок, чтобы длинные подписи и заголовки оставались в рамках макета
- сами SVG-макеты должны оставаться деловыми и чистыми: служебные подписи, mount/size-метаданные и внутренние helper-лейблы вроде `Навигация по помещениям`, `Настенное`, `Сообщение`, `Следующий шаг`, `Подписант`, `Карман 1` не должны печататься поверх реального носителя
- для `certificate` официальный режим должен оставаться максимально чистым: центральная надпись `Ямал`, аккуратная рамка и спокойная типографика без тяжёлой верхней плашки и случайных декоративных блоков
- для всех шаблонов используется общий fitter с безопасными внутренними полями: он старается сохранить полный текст без лишних троеточий и переносит дефисные/служебные токены более естественно
- для крупных headline-полей поверх этого нужны ещё более жёсткие safe-area коэффициенты, особенно в `social_post`, `presentation_deck`, `badge`, `certificate`, `letterhead` и `rollup`
- у `badge` safe-area для ФИО должна быть ещё более консервативной, чтобы длинное имя не врезалось в блок роли и нижнюю плашку доступа
- handoff-пакет тоже держит это оформление: HTML/JSON brief фиксирует выбранный цветовой вариант, логотип и элементы фона
- из текущего `SVG`-превью должна быть доступна честная клиентская выгрузка в `PNG`; это допустимый derived-export, но не повод притворяться, что у решения появился отдельный серверный `PNG`-рендер
- preview-контура и кнопочные панели конструктора тоже адаптируются под тип носителя, чтобы wide и tall шаблоны не ломали UI
- карточки и фильтры самой лаборатории держатся минимальными: без format-pills и без числовых бейджей внутри кнопок
- на карточках решений используются короткие summary, а не длинные абзацы, чтобы витрина читалась как деловой каталог
- рядом подбираются реальные разделы и реальные файлы каталога
